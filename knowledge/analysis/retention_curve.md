# 分析方法 · 留存曲线 / Cohort (Retention)

> 套路：按"注册周期"分组(cohort)，看每组用户在第 N 天/周后还回来多少，画留存曲线/热力图。
> 留存是产品健康度的核心，比单看 DAU 更能反映粘性。

## 何时用
"留存怎么样""新用户第7天还在吗""哪批用户留得好""cohort 对比"等。

## ⚠️ 先看曲线是不是衰减的 —— 这一步决定结论怎么写

**这条不是一句固定结论，是一个动作**：算完矩阵，先横着看一眼 W1→W4，再决定怎么落笔。
因为「这份数据算不出留存」这句话**取决于湖里装的是哪一批**，两批实测都在这儿：

| 批次 | 满窗 cohort 的 W1→W4（实测） | 该怎么写结论 |
|---|---|---|
| v1 种子样本（约 19 万行） | 第0→4 周 `45.0 / 43.0 / 42.1 / 41.1 / 43.0`，近乎水平、末周回升 | **数字照给 + 明说这份数据算不出留存** |
| 全量重灌批次（约 8000 万行，2026-09-17 实测） | `71.6 → 51.9 → 42.3 → 37.2`（W4/W1 ≈ 0.52） | 正常衰减，照常报留存结论 |

判据（不用记数字，看形状）：**W4/W1 ≥ 0.8 就是"不衰减"**，那是"数据没建模用户生命周期"
的特征——真实产品的留存必然前陡后平，D1 就该有明显断崖。这时**不要**把平坦曲线报成
正面业务结论（"曲线平稳、留得住""粘性好""忠实用户占比高"都属于这一类），要把
"这一批数据算不出留存"写进 `risk` finding。反过来，曲线确实在衰减时，**别再照抄这段警告**
——那是把已经修好的缺陷当成现状讲，同样是错的。

来历：曲线不衰减是 v1 生成器把活跃度与注册生命周期**独立抽样**的后果，项目审计把
「留存、流失、复购周期」整类列为不可信，原因就是这条 P0。新生成器给用户配了活跃半衰期
（`scripts/gen/tables.py` 的 `ENGAGEMENT_HALFLIFE`，会话挂在用户生命周期上），并且有一条
生成期闭合断言盯着它（L5.8「活跃量随注册后天数单调衰减」）——所以全量批次的曲线是衰减的。

反过来也不要过度纠正：**留存曲线小幅非单调（某周回升）是数据的真实性质，不是你的 SQL 错了**
（这一点和漏斗相反——漏斗非单调几乎总是口径错误，见 `funnel_analysis.md` 约束 A）。
两者的区别是：漏斗的单调性由 SQL 的子集约束保证，**留存的单调性只能由数据保证**。

> 还有一个与形状无关、两批都要说的：**部分周**。最早那个 cohort 常常只覆盖一周里的
> 一两天（注册窗口的左端切在周中），人数小、W1 偏高（实测 89.6%），那不是异常。
> 右下角三角的 0 是**右删失**（观测窗未到）。这两句都正确，但它们只解释边缘，
> **不能替代**上面对曲线形状的判断。

## ⚠️ 第二条，与形状无关：cohort 之间不可比

上一节判的是**曲线形状**（纵向：一个 cohort 随时间怎么掉）。这一节判的是**横向比较**
（cohort 之间谁留得好），两条独立，都要过。

全量批次的 cohort 全部出自同一个活跃度模型，它们的留存**在统计上没有差别**，
"哪批用户留得最好"这个问题在这份数据上没有答案。实测（2026-09-01，全量 7,994 万行；
注册后第 1 / 7 / 14 天的日留存，按注册周分组）：

```
2025-11-24  D1 59.5%  D7 23.3%  D14 14.8%   n=15,540
2025-12-01  D1 58.6%  D7 22.5%  D14 14.8%   n=15,843
2025-12-08  D1 58.9%  D7 22.0%  D14 14.3%   n=16,545
2025-12-15  D1 59.1%  D7 21.5%  D14 14.2%   n=17,106
2025-12-22  D1 59.2%  D7 21.3%  D14 13.9%   n=17,606
```

**满窗的几周之间 D1 只差 0.9pp、D7 只差 2.0pp**，这个量级是噪声。数据窗两头读出来偏高
（最早那周 D1 68.1% / D7 32.5%，人数只有 4,475）——**那是窗口边缘，不是"这批用户质量好"**。

两头偏高是**两个不同的机制**，2026-09-01 按天量出来的（每天 1,865–3,437 人，样本够）：

| 注册日 | 事件口径 D1 | 会话口径 D1 |
|---|---|---|
| 2025-10-26（窗首） | **80.8%** | 53.3% |
| 2025-11-02 | 66.7% | 55.0% |
| 2025-12-01（腹地） | 59.1% | 54.9% |
| 2025-12-15 | ≈59% | 55.6% |
| 2026-01-15 | 65.2% | 63.6% |
| 2026-01-22（轴末前 2 天） | **80.9%** | 80.0% |

- **右端（临近轴末）两个口径一起翘**。生成器把会话落在注册后第 k 天、`k` 的截断上限是
  **剩余窗口**，所以注册得越晚，同样约 10 次会话被压进越少的天数里（实测人均活跃天数
  从 5.1 天掉到 **2.3 天**），D1 被动升高。这是有限观测窗的固有产物，换 SQL 躲不开。
- **左端只有事件口径翘，会话口径是平的**（53.3% vs 54.9%，看不出边缘）。这一段
  多出来的 21pp 不是留存，是 `events` 的一个已知缺陷：保底事件
  （`purchase` / `use_coupon` / `register`，合计 118.6 万行）挂在用户的**首个会话**上、
  而时刻取的是**订单时刻**，于是订单越分散、事件跨的天数越多——窗首那批人均事件天数
  14.5 天 vs 腹地 8.3 天，而两者人均会话天数都是 5 天左右。详见
  `../domains/behavior/events.md`。

**所以按天/按周分 cohort 时，只报腹地那几期**（约 2025-11-25 … 2025-12-25），
两头各砍掉：左端砍到窗首后 30 天、右端砍掉 `D_max` 天。要少一层干扰就用
`sessions.start_time` 而不是 `events.event_time` 定义"回来"。

结论怎么落笔：给出矩阵 + 明说 **cohort 之间不可比、不要排名**，写进 `risk` finding。
照抄这句就行：

> cohort 之间不可比、不要排名：满窗那几周 W1 只差 2.9pp，所有 cohort 出自同一个
> 活跃度模型，"哪批留得最好"没有可读答案。

**不要**答成"某批 cohort 留得最好/最差"（"10 月那批粘性最强""越新的 cohort 越差"）。
**也不要**把"几乎重叠"翻译成正面业务结论——"这批新客的留存质量高度一致"
"各周拉来的用户一样稳"都属于这一类：几条曲线重合是同一个活跃度模型抽出来的，
不是这些用户的质量。实测栽过一次，判红的就是这种写法。
绝对水平也别当业务基准：它由生成器的活跃度模型定（四组活跃半衰期 1 / 5 / 20 / 60 天，
权重 40/30/20/10，`k ~ 截断指数分布`），不来自任何真实产品。

全量批次的整体日留存（取注册日在轴末 15–56 天之间的 10.3 万人）是
`D0 100% → D1 59.4% → D2 47.1% → D3 36.9% → D7 22.3% → D14 14.7%`：单调衰减、断崖在 D1
（D0 = 100% 是生成器给每个用户保底一个注册会话的结果）。
**日粒度上算出明显非单调，先查自己的 SQL**——这一批数据的单调性是生成器保证的。

## 统计公式（Cohort 留存，请照此算并填进 method）
设某 cohort 初始人数 N₀，第 t 天仍活跃人数 Nₜ：
- **第 t 天留存率**：Rₜ = Nₜ / N₀ —— 留存曲线纵轴。
- **常看点**：R₁（次日）、R₇（7日）、R₃₀（30日）。
- **区间流失率**：第 t→t+1 的流失 = (Nₜ − Nₜ₊₁) / Nₜ。
- **断崖点**：Rₜ 相邻两期跌幅最大的地方（通常在 D1，反映激活质量）。
> 曲线一般前陡后平；若长期趋于水平线，那条渐近线 ≈ 产品的"忠实用户占比"。

## 硬约束 · 分子必须限定在 cohort 成员内

Rₜ 的分子是「**这个 cohort 里**第 t 期还活跃的人数」，不是「第 t 期全站活跃人数」。
SQL 上就是活跃表必须 `JOIN` 上 cohort 成员名单（`ON act.user_id = coh.user_id`），
**不能只按时间筛活跃再除以 cohort 人数**。

漏掉这一步的后果很好认：**留存率会超过 100%**。实测过——分子取成全站活跃时，
第 1 周是 219 人 / cohort 43 人 = **509%**。所以**算完先看一眼有没有 >100% 的格子**，
有就是分子没限定住。（这和 `funnel_analysis.md` 的约束 A 是同一个毛病：
"没说清子集关系"。漏斗那次是悄悄给个像样的数，留存这次会直接炸出 500%。）

## 做法（这几步填进 present_result.method.steps）
1. **定义 cohort**：按 users.registered_at 的周(或日)分组。
2. **定义"回来"**：该用户在注册后第 N 天/周有 events 活跃（或有订单，看问题）。
3. 算每个 cohort 在第 0/1/7/14/30 天的留存率 Rₜ =
   **该 cohort 成员中**该期活跃数 / cohort 初始人数（见上面的硬约束；
   把 R₁/R₇/R₃₀ 填进 method.stats）。
4. 也可用 mart_user_summary 的 last_active_date 做粗略"是否近期活跃"判断。
5. 找规律写 `findings`：留存曲线在第几天断崖（跌幅最大处）、断崖后衰减到哪个水平。
   **这一步不许写"哪批 cohort 留得最好/最差"**——2026-09-01 之前这里写的就是那句，
   与顶部那条冲突，实测到 agent 照它答了比较级。要写的是"cohort 之间不可比"。

## 输出要求
- chart 优先用 `heatmap`：xLabels=第N天/周, yLabels=各 cohort, cells=留存率。
  也可用 line 画几条代表性 cohort 的留存曲线对比。
- KPI：次日留存、7日留存、30日留存（整体）。
- insight 点出留存断崖位置（这份数据在 D1）。**不要点"最佳/最差 cohort"**，
  也不要把"几条曲线重合"写成"用户质量一致"——见顶部那条，满窗几周之间
  W1 差 2.9pp、日粒度 D1 差 0.9pp，这个量级是噪声。
- **risk finding 里必须有一句"cohort 之间不可比、不要排名"**，判分器盯的就是它。
  只写右删失不算数（下面单列了一条说明原因）。
- 注意：近期注册的 cohort 还没到第30天，**留存窗口不完整不能和老 cohort 比**，放进 risk finding。
  热力图右下角那片 0 是**右删失**（观测窗未到），不是真实下跌，要说明。
- **但右删失这条不能替代顶部那条**：观测窗说明只解释了"边缘的 0"，
  没解释"满窗那几周之间为什么不能排名"。两条都要写，只写前一条会让整段话听起来严谨、
  而结论仍然是错的。
